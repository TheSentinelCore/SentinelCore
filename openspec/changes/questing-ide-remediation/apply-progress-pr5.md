## The zone derivation, and why it is what it is

`creature` has map + position and no zone; `creature_zone` has zero rows. The client data does have
the answer, and mangos's own runtime path is the specification (`GridMap.cpp`, `DBCStores.cpp`):

1. grid tile `gx = int(32 - x/533.33333)`, `gy` likewise → `maps/%03u%02u%02u.map`
2. area **BIT** from the tile's 16×16 grid — `AreaTable.m_AreaBit`, **not** an area id
3. `AreaTable` row keyed by that bit (mangos indexes `sAreaStore` on field 3, hence `"iiin…"`)
4. zone = `ParentAreaID`, or the area's own id when that is 0

Coverage: **109,305 of 109,352** creature spawns and **72,339 of 72,385** gameobject spawns.
The 47 and 46 that do not resolve are out-of-world coordinates on Kalimdor and Alterac Valley;
they are reported in the catalog's `unresolved_by_map`, not invented. Both the generator and the
Lua test assert the unresolved fraction stays under 0.1%.

## Deviations from Design and Spec

1. **`zone_names.rs` is replaced, not regenerated.** The prompt asked for the generator to emit the
   139-row table and for a check that the committed table matches regeneration. Deleting the table
   is strictly stronger: a match check between two generated copies still leaves two copies, and
   the table could not name a zone `quest_template` never mentions — which `/zone/{id}/spawns`
   needs on every request. The coverage guarantee survives as a test against the **live DB**
   (`every_zone_a_quest_names_resolves_to_a_name`), which is what the frozen list asserted by
   construction.
2. **The spawn index stores `(zone, entry, count)`, not GUID → zone.** The spec says the endpoint
   joins "the spawn-zone index with `creature` + `creature_template`"; the join is against
   `creature_template` only. Both endpoints aggregate per entry immediately, so 109k committed GUID
   rows would have had no reader, and positions are already served by `/spawns/{type}/{entry}` and
   `/spawns/nearby`. The response shape is exactly as specified.
3. **`SpawnGroup` carries `avg_level`, not a range.** Spec's shape for the zone endpoint names
   `avg_level`; a creature entry is a level range in mangos, so `(MinLevel + MaxLevel) / 2`. A range
   needs two fields and a spec change.
4. **A taxi segment must carry positions.** Spec's request shape is `{type:"taxi", from_node,
   to_node}`. That is accepted and echoed, but without `from`/`to` the segment is a 400: this
   server has no taxi tables, `TaxiPathNode.dbc` is in no committed catalog, and the runtime does
   own node positions in `taxi_nodes.lua`. The alternative was a fabricated per-hop constant
   sitting silently in the editor's total.
5. **`exploration_level`, not `level`, in the zone catalog.** `AreaTable.m_ExplorationLevel` is 0
   for every top-level zone (the client awards exploration XP per sub-area). A field called `level`
   would render "Elwynn Forest, level 0".
6. **`radius` is horizontal and capped at 2,000 yards.** The request carries no `z`, and an
   uncapped radius stops being a plan.
7. **Two PR4 open items left alone, as instructed**: `MaxLevel` is still not exposed, and
   `classification` still emits 5 values because mangos `Rank 2` is "rare elite". Both need a spec
   decision, not a code change.
